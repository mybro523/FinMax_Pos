# FinMax POS — касса и склад магазина

Автоматизация продаж магазина: продажа по сканеру штрихкода (USB и камера телефона),
учёт остатков, приход товара (в том числе в долг поставщику), оплата (наличные / карта /
в долг / переводом через Alif, DC, Эсхата…), авто-заявка, долги клиентов и поставщикам,
расходы магазина, внесение и изъятие наличных в смене, история движения товара,
отчёты с чистой прибылью и дашборд.

Монорепозиторий:
- **`client/`** — фронтенд: React + Vite (деплой на **Vercel**)
- **`server/`** — бэкенд: NestJS + Prisma + PostgreSQL (деплой на **Railway**)
- **`desktop/`** — программа для Windows: Electron + тот же интерфейс из `client/`

Данные общие для всех устройств — касса на ПК и телефон видят одну базу.

## Локальный запуск

### 1. Бэкенд
```bash
cd server
cp .env.example .env        # пропишите DATABASE_URL (локальный Postgres)
npm install
npx prisma db push          # создать таблицы
npm run start:dev           # http://localhost:3000/api
```
База авто-наполнится демо-данными при первом запуске (если пустая).

### 2. Фронтенд
```bash
cd client
npm install
npm run dev                 # https://localhost:5180  (/api проксируется на :3000)
```

### 3. Программа для Windows
```bash
cd desktop
npm install
cp .env.example .env        # адрес сервера: APTEKA_API_URL=https://…/api
npm run electron:dev        # программа с живой подменой кода интерфейса
npm run electron:build      # установщик → desktop/release/FinMax-POS-Setup-<версия>.exe
```
Интерфейс у программы тот же, что у сайта: он собирается из `client/` в режиме
`desktop` (адреса разделов после решётки, пути от самой страницы, свой шрифт).
Сайт при этом собирается по-прежнему — режим выбирается только при сборке программы.

Чем программа отличается от вкладки браузера:
- ключ входа лежит не в окне, а в основной части программы, зашифрованный средствами
  Windows; окно знает только, что вход выполнен;
- окну закрыт интернет: все запросы к серверу идут через основную часть;
- адрес сервера зашивается при сборке и на компьютере магазина не меняется.

**Работа без интернета.** Касса всегда работает с локальной базой (SQLite в папке
данных программы, по файлу на магазин) — и когда связь есть, и когда её нет:
- без интернета доступны продажа (наличными, картой, в долг, переводом), возврат,
  смена с внесением и изъятием наличных, погашение долга, приход (в том числе в долг
  поставщику, которого касса уже знает) и списание уже заведённого товара, отложенные
  штрихкоды, новый расход магазина (в том числе из кассы), просмотр товаров, поставщиков,
  журналов и отчётов за последние дни;
- заведение и правка товаров, сотрудники, пересчёт остатков, настройки, правка и
  удаление расхода, статьи расходов, заведение и оплата поставщиков, отмена внесения
  и изъятия, сервисы перевода, история движения товара и отчёты за давние периоды —
  только с интернетом (программа так и говорит);
- первый вход на компьютере идёт через сервер, дальше тот же сотрудник входит и без
  связи: пароль проверяется на месте по необратимому отпечатку;
- остаток считается по журналу движений: свежие данные сервера становятся основой,
  а сделанное на кассе и ещё не отправленное накладывается поверх;
- каждая операция записывается с номером, созданным на кассе, и встаёт в очередь
  на отправку.

**Обмен с сервером.** Идёт сам, в фоне, в два шага и всегда в этом порядке:
1. *Отправка* (`POST /api/sync/push`): всё сделанное на кассе уходит пачками, по порядку.
   Сервер узнаёт повтор по номеру операции, поэтому после обрыва связи пачку можно
   просто послать ещё раз — ни второго чека, ни второго списания не будет.
2. *Получение* (`GET /api/sync/pull`): касса спрашивает «что изменилось с прошлого раза»
   и получает только это (в первый раз — всё). Что менялось, записывает сама база
   сервера (журнал изменений), поэтому мимо обмена не проходит ничего — ни продажа
   с сайта, ни правка цены.

Связи нет — попытка повторяется с нарастающей паузой (5, 10, 20, 40, 60 секунд);
появилась — обмен начинается сам. Чек, пробитый с интернетом, уходит через секунду.

Про операцию, которую касса отправила, а ответа не дождалась, она спрашивает при
получении: «вот её номер — принята?». Сервер отвечает из того же состояния базы, из
которого отдаёт данные, поэтому касса точно знает, какие её операции в этих данных уже
есть, а каких ещё нет, — и ни одну не считает дважды, чем бы ни кончилась отправка
(даже если повторить её нечем: кассиру сменили пароль).

Номер кассы закреплён за ключом, который создаётся на ней при первом запуске и уходит
на сервер заголовком `X-Device-Key`. Под этим номером сервер слушает только того, кто
назвал тот же ключ: кассир с соседней кассы не может закрыть чужую смену или вписать
в неё свои чеки, даже зная номер.

Если базу сервера поднимали из копии или переносили на другой сервер, кассы узнают
об этом сами. Сервер помнит, какую отметку обмена он выдал каждой кассе; касса,
которая называет отметку новее (она успела получить то, чего в базе теперь нет),
получает весь магазин заново, а не «изменения». Своё неотправленное касса при этом
не теряет. Владелец может сделать то же руками: «Состояние программы» →
«Загрузить всё заново».

Операция кассы уже случилась (товар отдан, деньги взяты), поэтому сервер её не
«разрешает», а записывает. То, что при этом не сошлось с базой, он показывает
владельцу в блоке **«Расхождения с касс»** на панели управления:
- продано или списано больше, чем было (две кассы без связи продали одну и ту же
  последнюю упаковку) — остаток становится нулём, а не минусом;
- цена в чеке не та, что была в базе в момент продажи (цену сменили, пока касса была
  без связи, — или её подправили на самой кассе). Сверяется с историей цен;
- по чеку вернули больше, чем по нему продали;
- операция сделана до пересчёта остатка, а пришла после. Пока касса была без связи,
  остаток могли пересчитать (инвентаризация) или поправить в карточке товара — считали
  то, что лежит на полке, и проданного кассой там уже не было. Вычесть эту продажу
  ещё раз значило бы посчитать её дважды, поэтому документ записывается, а остаток
  не двигается. Если пересчёт был инвентаризацией, её итог поправляется сам: лист
  считал «должно быть» без этой операции и записал проданное в недостачу — теперь
  «должно было быть» и недостача по товару приводятся к настоящим (недостача
  уменьшается на проданное и списанное, растёт на принятое). Итог не зависит от того,
  в каком порядке кассы прислали свои операции: «должно было быть» по ходу может
  оказаться и отрицательным (продажа дошла раньше прихода, который был до неё), а две
  кассы, приславшие операции разом, поправляют лист по очереди. Правка остатка в
  карточке считается таким же пересчётом одного товара. Отметки о пересчётах хранятся
  полтора месяца; после этого у товара остаётся одна, последняя: касса, вышедшая на
  связь через два месяца, остаток уже пересчитанного товара не сдвинет, но и итог
  давнего листа по её операциям не поправляется — владелец видит расхождение;
- клиент заплатил (или ему зачли возвратом) больше, чем он был должен: долг успели
  погасить на сайте или на другой кассе.

Отказ — только для того, что нельзя записать без вранья: суммы не сходятся с позициями
(разница в дирам на позицию — это округление, а не порча, и чек принимается с суммой
кассы), чека для возврата нет, операцию прислали от чужого имени. Отвергнутое остаётся
на кассе с пометкой, а всё, что касса держала «поверх» него, снимается: отвергнутая
смена не считается открытой, отвергнутый клиент исчезает, отвергнутый возврат не
мешает вернуть товар снова. В журналах кассы отвергнутой операции больше нет, поэтому
владелец видит её целиком в окне «Состояние программы»: все позиции с количеством и
ценой, оплату, клиента, срок годности в приходе, чек у возврата — по этому её можно
оформить заново. Закрытие смены, которое сервер не принял, сразу возвращает смену
открытой: второй смены поверх неё не открыть, чеки идут в неё же. Исключение — сервер
ответил, что такой смены для этой кассы у него нет (его базу вернули из старой копии,
базу кассы перенесли с другого компьютера): тогда смена остаётся отвергнутой, кассир
открывает новую, и её сервер принимает. После отказа касса сама забирает у сервера всю
магазин заново: отказ значит, что они разошлись в том, что считают правдой, и касса
берёт то, что знает сервер. Если полная загрузка не прошла, следующий заход идёт только
за изменениями — и по нему видно, в чём дело. Он тоже не прошёл — связи нет вовсе:
как только она появится, касса снова попросит всё (ждать приходится минуту с
небольшим, а не полчаса). Он прошёл — не проходит именно большой ответ: изменения идут
как обычно, а весь магазин касса пробует забрать через 5 секунд, 15, минуту, две и
дальше раз в пять минут.

Числа больше тех, что принимает сервер, касса не оформляет вовсе — отказ сразу, а не от
сервера потом: сумма с лишними нулями, сто миллионов упаковок, больше двух миллиардов
штук в строке, товар, у которого в карточке больше ста тысяч штук в упаковке (сайт
такую карточку теперь тоже не сохранит). То же со сроком годности, где в годе лишняя
цифра («20266» — поле даты в браузере это пускает): такую дату база не хранит. Раньше
сайт отвечал на неё «внутренняя ошибка сервера», а операцию кассы с таким сроком сервер
не смог бы записать никогда — и за ней встала бы вся очередь кассы; теперь и сайт, и
касса отказывают сразу и понятными словами. Если сервер несколько раз подряд не может
записать одну и ту же операцию, значок состояния говорит об этом — за ней стоит вся
очередь.

Смена у каждой кассы своя (без связи касса не знает, открыта ли смена на соседней);
смена на сайте — отдельная, как раньше. Закрытые смены всех касс видны в общей истории.
Смену кассы, которая сама её уже не закроет (компьютер сломался, программу
переустановили), закрывает владелец: «Настройки» → «Кассы» → «Закрыть смену». Чеки,
которые касса ещё пришлёт, попадут в итоги этой смены.

Возврат по чеку старше двух месяцев (у кассы его уже нет) оформляется так же, как
любой другой: касса забирает чек с сервера и записывает возврат у себя — в своей смене
и из своего денежного ящика.

**Расходы магазина** (раздел «Расходы», только владельцу) — аренда, зарплата, налоги и
всё прочее, на что магазин тратит деньги помимо закупки товара. В «Отчётах» они
вычитаются из прибыли: «Чистая прибыль» = прибыль на товаре − расходы за период.
Статьи расходов — готовый список плюс свои («Настройки» → «Статьи расходов»); расход
хранит статью названием, поэтому убранная статья остаётся в прежних расходах.

Расход с отметкой «Оплачен из кассы» привязан к открытой смене и уменьшает наличные,
которые в ней ждут, — иначе смена не сошлась бы ровно на эту сумму. Сумму таких
расходов сервер ведёт в самой смене (`Shift.expenseCash`): страница смены показывает
её и кассиру, которому сам раздел закрыт, и с ней же смена уходит на кассы с
программой. Дата расхода из кассы — всегда «сейчас»; править и удалять его можно,
пока смена открыта, — после закрытия он остаётся в её Z-отчёте. На сайте владелец
выбирает, из какой кассы взяты деньги (смена сайта или открытая смена кассы с
программой); в программе касса всегда своя.

В программе расход вносится и без интернета. Пока сервер его не принял, касса сама
прибавляет его к сумме смены; принял — прибавка переходит в сумму смены, и свежая
копия смены с сервера её просто подтверждает. Так расход из кассы не теряется и не
считается дважды ни в одном из промежуточных состояний, включая обрыв связи сразу
после отправки. Расходы и статьи сервер отдаёт кассе только при обмене владельца —
как журнал списаний. При обновлении программы с версии 1.0.0 отметка «докуда
получены разделы владельца» сбрасывается: первый обмен владельца приносит расходы и
статьи целиком.

**Приход товара** — один экран: слева поставщики (выбранный фильтрует все вкладки и
становится поставщиком нового прихода), сверху период, вкладки «Поступления · Новое
поступление · Возврат · Платежи и баланс · Отчёты». Новое поступление — накладная таблицей,
итоги тёмно-синей панелью и форма под таблицей; набранное живёт в памяти программы
(`client/src/pages/prihod/store.js`), а не в окне, и не теряется при переключении.
В строке — «упаковки + штуки» у делимой упаковки и скидка поставщика, %: закупочная
цена (`ArrivalItem.cost`) записывается уже со скидкой, сам процент — в
`ArrivalItem.discount`. Расчёты строки и итогов — `client/src/lib/prihod.js`.

**Возврат поставщику** — вкладка «Возврат» прихода (право «Приход товара: возврат
поставщику»; удаляет владелец). Товар уходит со склада партиями с ближайшим сроком,
просроченные тоже; цена строки — последний приход от этого поставщика, иначе закупочная
из карточки. Деньги — «в счёт долга» (долг уменьшается, не больше, чем он есть), «в
кассу» (наличные в ящик открытой смены: `Shift.supplierRefund` прибавляется к
«ожидается в кассе» и печатается в Z-отчёте), «наличными» мимо кассы или «на карту».
Документ — `SupplierReturn` с партиями в строках (`SupplierReturnItem.batches`):
удалённый возврат кладёт товар в те же партии. Возврат «в кассу» закрытой смены не
удаляется. В сверке поставщиков — колонка «Возвращено» (долг на конец = на начало +
закуплено − возвращено − оплачено), в ОПУ деньги поставщика уменьшают «Оплату
поставщику». Программа для Windows оформляет возврат и без интернета (операция
`supplier.return`); удалить его можно только с интернетом.

**Поставщики и долги им** (раздел «Поставщики», только владельцу). Справочник
поставщиков (название, телефон, примечание, долг на начало); в приходе — поставщик из
справочника и «Чем заплатили»: из кассы, наличными, картой или в долг — что не
оплачено сейчас, становится долгом перед ним (`Arrival.debt`, `Supplier.debt`). В
карточке поставщика и на вкладке «Платежи и баланс» прихода — приходы, оплаты и
кнопка «Записать оплату»; оплата с отметкой «из кассы» привязана к открытой смене и
уменьшает наличные, которые в ней ждут (`Shift.supplierCash`), но расходом не
считается — товар уже лёг в закупочную цену. Правка и удаление прихода пересчитывают
долг. Дашборд показывает общий долг поставщикам. Кассиру список поставщиков отдаётся
без долгов. Старые приходы считаются оплаченными.

**Внесение и изъятие наличных** — кнопки «Внести» и «Изъять» на странице смены
(владельцу и кассиру): размен положили, выручку забрали. Запись (`CashMove`)
принадлежит открытой смене, входит в «ожидается в кассе» и в Z-отчёт отдельными
строками с автором; пока смена открыта, владелец может отменить запись. Формула
смены теперь такая: ожидается = на начало + наличные продажи + погашения долгов +
внесено − наличные возвраты − расходы из кассы − оплаты поставщикам из кассы − изъято.

**Оплата переводом** — четвёртый вид оплаты на кассе с выбором сервиса (Alif, DC,
Эсхата, Humo, Амонат — список свой, «Настройки» → «Сервисы перевода»). Сервис
хранится в чеке названием (`Sale.payVia`), в возврате переводом — тоже
(`SaleReturn.refundVia`); смена и отчёты показывают переводы отдельно и по сервисам
(`Shift.salesTransfer`, `Shift.transferBy`), чтобы сверять с выпиской каждого.

**История движения товара** — кнопка в строке товара (владельцу): приходы, продажи,
возвраты, списания, пересчёты и правки остатка в карточке (`StockEdit`) с датой,
количеством со знаком, автором и остатком после. История собирается из самих
документов, поэтому прошлое в ней есть и у давно заведённых товаров.

Отложенный чек был и раньше: вкладки чеков на кассе («Отложить чек», F8) хранятся
на устройстве.

В программе без интернета работают приход в долг известному поставщику, внесение и
изъятие, продажа и возврат переводом; долг поставщика на кассе складывается из того,
что знает сервер, и своих неотправленных приходов — как остаток товара. Оплата
поставщику, её отмена, отмена внесения, сервисы перевода и история товара — только с
интернетом; оплату «из кассы» программа сама привязывает к смене своей кассы. При
обновлении программы с версии 1.0.1 сбрасываются обе отметки «докуда получили»:
поставщиков и сервисы перевода сервер отдаёт всем, но прежняя версия их не брала, и
первый обмен приносит всё заново — один раз.

Товар, который возвращается в продажу, получает срок годности — иначе он выпал бы из
контроля сроков. Из какой партии продана пачка, при продаже не записывается, поэтому
срок ставит программа: самый ранний среди партий товара, годных в день покупки, в том
числе уже распроданных. Продажа берёт партию с ближайшим сроком, так что настоящий срок
пачки не раньше этого — ошибиться можно только в осторожную сторону. (Раньше
возвращённое получало срок партии, лежащей на складе: при пустом складе — никакого, а
когда свою партию уже распродали — более поздний, чем настоящий.) Точный срок кассир
может вписать сам, с коробки, в поле «Срок на упаковке» окна возврата; истёкший срок в
продажу не принимается — такой товар списывают. Без связи срок ставит касса по тем
партиям, что знает. Приняв возврат, сервер ставит срок по своим партиям — он знает их
все, — если только кассир не вписал срок сам. Товары без срока (бинты, приборы)
остаются без срока.

Журналы обмена (что менялось, движения товара) сервер подчищает сам раз в сутки — у
каждого магазина, есть у него кассы с программой или нет.

Лист пересчёта меняют по одному: сохранение насчитанного, применение, удаление и
поправка недостачи операцией кассы берут лист под замок. Применение читает лист уже
под замком — повторное применение того же листа получает «уже применён», а не проводит
его второй раз. Страница пересчёта присылает насчитанное вместе с просьбой применить —
одним запросом (`POST /inventory/:id/apply` с полем `items`); сервер записывает его и
применяет лист одной записью, под одним замком, так что сохранение черновика,
отправленное раньше, эти числа не подменит. Если применить не вышло, присланное
сохраняется в листе отдельно. Само применение короткое: товары читаются пачками,
записывается только изменившееся (три тысячи товаров — от секунды, когда расхождений
мало, до нескольких секунд, когда расхождение в каждой строке), и продажи на это время
не встают.

Лист считают часами и с разных устройств, поэтому страница не считает его «своим»
(`client/src/lib/pereschet.js`):
- лист открывается свежим (`GET /inventory/:id`), и перед вопросом «применить?»
  страница берёт его с сервера ещё раз — итог в вопросе тот, что будет применён;
- на сервер уходят только строки, изменённые на этом устройстве. Раньше уходил весь
  лист таким, каким его видела вкладка, и вкладка, открытая с утра, стирала пустотой
  числа, внесённые за день с телефона;
- введённое лежит на устройстве, пока сервер его не принял: оно переживает и отказ
  связи, и перезагрузку страницы;
- чем кончилось применение, страница не додумывает. Ответ потерялся — она спрашивает
  сервер (`GET /inventory/:id?wait=1` отвечает после того, как закончится идущее
  применение). Лист применён с теми же числами — всё в порядке; применён с другими
  (успели с другого устройства) — страница говорит об этом, а не показывает «остатки
  обновлены»; узнать не удалось — так и говорит, а не «не применён»;
- сервер обновляется на минуты позже сайта. Прежний сервер чисел в «применить» не
  понимает и применил бы лист без них, поэтому ему страница шлёт их по-старому —
  отдельным запросом перед «применить».

Считает локальная база теми же формулами и с теми же округлениями, что сервер.
Это проверяется на настоящем сервере, без заглушек:
- `npm run test:parity` проводит один и тот же рабочий день на сервере и в локальной
  базе и сравнивает каждый документ, остаток и текст отказа;
- `npm run test:sync` — продажа без интернета, возвращение связи, повторная отправка
  без дублей (ответ сервера теряется), обрыв связи посреди обмена, две кассы и
  последняя упаковка, смена цены и повторный возврат.

Обе проверки пишут настоящие продажи — запускать только на своём проверочном магазине.

**Значок состояния.** В шапке программы всегда видно, сохранено ли сделанное: «Всё
отправлено», «Отправка: 3», «Нет интернета · ждут отправки: 12». По нажатию — окно
«Состояние программы»: последний обмен, что не принял сервер (видит владелец), сколько
ещё можно работать без связи, копия базы, обновление.

**Срок работы без связи.** Подписку проверяет сервер — при каждом обмене. Без связи
с ним программа работает не дольше заданного числа дней (по умолчанию 7), потом
останавливается до первой удачной проверки. Число своё у каждого магазина: его задаёт
владелец сервиса в карточке магазина («Касса работает без связи, дней», от 1 до 30).
Отметка о последней проверке лежит на диске зашифрованной — вместе с моментом, до
которого программа уже дожила. Перевести дату и получить ещё неделю не выйдет.

**Часы программы.** Время чека — серверное: поправка к часам компьютера берётся из
каждого ответа сервера и запоминается. Перевод часов компьютера, пока программа
работает, на её время не влияет. Чего программа не знает, она не выдумывает: если
после запуска часы компьютера показывают время раньше уже виденного (их перевели
назад или села батарейка на плате), время продолжается с последнего увиденного момента,
а значок и окно состояния говорят прямо — «проверьте часы компьютера». Дату и время
поправили — программа берёт их сразу, без перезапуска; ошиблись (не тот месяц) и
поправили ещё раз — тоже: время при этом не раньше того, что программа насчитала сама.
Окно состояния показывает время программы, пока оно не сверено с сервером. Первый же
ответ сервера возвращает обычный порядок. Запомненной поправке больше полусуток
программа верит, только если без неё время выходит раньше уже виденного: после починки
часов она не окажется в 2038 году.

У срока работы без связи — свой отсчёт. Он не идёт за часами компьютера, которым
нельзя верить: опечатка в дате не запрёт кассу до появления интернета. А за запуск со
сбитыми часами (сколько программа была выключена, узнать не у кого) срок уменьшается
так, как если бы компьютер был выключен «как обычно». Что значит «обычно», программа
знает сама: пока часам можно верить, она запоминает, сколько часов простоя приходится
у этого компьютера на час работы. Магазин, где компьютер работает десять часов и
выключен четырнадцать, получит за ночь свои четырнадцать; круглосуточная, где свет
мигает трижды в день, — почти ничего. Иначе на компьютере с севшей батарейкой неделя
без связи либо растягивалась бы на две с половиной, либо сгорала бы за три дня.
Целиком закрыть лазейку без связи нельзя: кто каждое утро аккуратно ставит на
компьютере вчерашнее время закрытия, выгадывает ночи.

**Копия локальной базы.** Раз в сутки программа снимает копию своих баз в папку
`backups` рядом с данными и хранит семь последних; каждая копия сразу проверяется.
Испорченный файл базы при запуске сам поднимается из последней исправной копии (и
программа говорит об этом); так же — если файл пропал или пуст, а копия есть. Всё, что
осталось от прежней базы (сам файл и его журналы с записями последних минут), не
стирается, а откладывается в папку `broken`. Пустой файл базы копией не становится.
Какая копия свежее, решает порядковый номер в имени папки, а не время: ни перевод
часов, ни севшая батарейка порядок копий не меняют. Владелец может
выбрать вторую папку — на другом диске или флешке: копия на том же диске не спасёт от
сломанного диска. Во второй папке у каждого компьютера своя подпапка (его имя и
отпечаток полного имени — так различаются и компьютеры, названные по-русски): одной
папкой могут пользоваться две кассы, и чужую копию касса не поднимет. Копия снимается и перед
установкой обновления. Одна испорченная база не оставляет без копии остальные, а
последняя копия каждой базы не удаляется, сколько бы ей ни было.

**Обновление.** Программа сама проверяет, нет ли новой версии, скачивает её и ставит
при закрытии — или сразу, по кнопке «Перезапустить и обновить». Посреди работы она
не перезапускается никогда. Откуда брать обновления, зашивается при сборке:
```bash
# desktop/.env
APTEKA_UPDATE_REPO=владелец/репозиторий   # открытый репозиторий GitHub с установщиками
```
Выпуск новой версии: поднять `version` в `desktop/package.json`, задать ключ GitHub
в переменной окружения `GH_TOKEN` (в файлы проекта его не класть) и выполнить
`npm run electron:publish` — установщик и описание версии уйдут в репозиторий, и
программы в магазинах обновятся сами. Ключу хватает доступа к одному этому репозиторию
с правом «Contents: Read and write».

Выпуск заводится черновиком ещё до сборки и открывается в самом конце — только когда
в нём лежат установщик, его карта и описание версии (`desktop/scripts/github-release.mjs`).
Иначе упаковщик, выкладывая файлы двумя потоками, создаёт выпуск дважды, второй поток
получает от GitHub отказ, и магазины видят «новую версию» без установщика. Оборвалась
выкладка — выпуск остаётся черновиком, магазины его не видят; команду можно повторить.
Уже открытую версию подменить нельзя: нужен новый номер.

Перед выпуском стоит выполнить `npm run test:update`: он по-настоящему ставит
проверочную сборку, обновляет её и удаляет (см. шапку `desktop/scripts/check-update.mjs`).
После выпуска — `npm run test:release`: он скачивает выложенный установщик по общей
ссылке, без ключа, как это сделает магазин, сверяет его с описанием версии, ставит,
входит проверочным магазином, убеждается, что программа сама нашла свой репозиторий
обновлений, и удаляет её (см. шапку `desktop/scripts/check-release.mjs`).

**Сканер и печать.** Сканер штрихкодов работает как клавиатура — так же, как на сайте
(это проверяется: программа получает код с задержкой в миллисекунды между знаками и
завершающим Enter).

**Чек: отмена, повтор, номер (с 1.5.3).** В окне чека после продажи есть «Отмена»:
продажа отменяется возвратом всего чека с пометкой «Отмена чека» (`client/src/lib/otmena.js`) —
товар на полку, деньги тем же способом, — и чек возвращается в корзину. Отмену видно в
журнале возвратов, в Z-отчёте («в т.ч. отмены чеков»), в истории долга клиента и во
вкладке «Чеки» «Отчёта продажи»; продажей отменённый чек не считается. Во вкладке «Чеки» —
каждый чек строкой, по клику — сам чек и «Печать» (повтор без пометок; у отменённого — строка
«Чек отменён …»). Номер чека —
из времени продажи, поэтому касса показывает и печатает чек по уже записанной продаже:
номер на бумаге совпадает с номером в отчётах и при поиске. Долг клиента печатается
выпиской (`client/src/lib/dolg.js`, `debtTicket`): покупки, отмены и возвраты, погашения;
всё, что старше истории устройства, — строкой «Прежний долг до <даты>», чтобы итог сходился.

**Печать везде одинаковая.** Всё, что идёт на бумагу, рисуется в печатном слое
(`client/src/components/PrintDoc.jsx`) — отдельно от страницы, поэтому лишних пустых
листов нет. Оформление фирменное, как у «Отчёта о прибылях и убытках»: тёмно-синяя
шапка с магазином, названием листа и датой, синяя строка заголовков (она повторяется
на каждом листе), итог синей строкой, внизу — название магазина и «стр. N из M».
Чек, чек возврата и Z-отчёт — с названием магазина на синей полосе, итогом на синей
плашке и ещё раз названием магазина внизу; этикетки — с ценой на синей плашке. Бумага
и экран покупателя — магазина: эмблемы и имени программы на них нет (с 1.5.2). На сайте печатает окно браузера (у него
свой предпросмотр). В программе для Windows окно печати Windows предпросмотра не
умеет, поэтому у неё свой экран печати (`client/src/components/PrintPreview.jsx`):
страницы точно как из принтера (PDF печатного слоя, нарисованный pdf.js), принтер,
книжная или альбомная, копии, «Печать» без окна Windows и «Сохранить в PDF»; у чека —
ещё «лента 58/80 мм или лист A4», и лента показывается строками, как её разложит
чековый принтер. Если в
магазине стоит чековый принтер, владелец включает его в «Настройках» → «Печать чеков»:
- *по сети* (принтер с сетевым гнездом, порт 9100) или *подключённый к компьютеру*
  (заведён в Windows; задание уходит в его очередь «сырым», мимо драйвера). Адрес
  сетевого принтера — только из сети магазина (192.168.x.x, 10.x.x.x, 172.16–31.x.x):
  окну программы интернет закрыт, и печать не должна стать дорогой наружу;
- лента 58 или 80 мм, таблица букв CP866 или CP1251, отрез, денежный ящик,
  печать чека сразу после продажи;
- чек и Z-отчёт уходят в принтер строками на языке ESC/POS — без окна печати; название
  магазина и итог печатаются белым по чёрному во всю ширину ленты.

Чековые принтеры не знают таджикских букв: вместо «қ» печатается «к». Как чек выглядит
на бумаге у конкретной модели, показывает кнопка «Пробная печать» — проверить это без
самого принтера нельзя. Не настроен чековый принтер или он выключен — продажа всё
равно проходит, а печать идёт обычным путём или показывает, что не так.

**Принтер этикеток (с 1.5.4).** Наклейки со штрихкодом печатаются из «Товаров» (значок
ярлыка в строке товара → «Печать этикеток» → «Наклейки», поле «Сколько наклеек») и на
весь приход сразу («Приход · детали» → «Этикетки»: у каждой строки число наклеек — сколько
упаковок пришло, неполная упаковка — тоже наклейка, весовой товар — одна; поправить можно).
«Лист A4» с сеткой этикеток для обычного принтера остался. Принтер выбирают в «Настройках» →
«Чек и печать» → «Принтер этикеток» (настройка компьютера, `desktop/src/print/labels.mjs`):
принтер Windows, размер наклейки (58×40, 58×30, 40×30, 30×20 или свой, 25–110 × 20–150 мм),
разрешение принтера (203 или 300 dpi), сдвиг вправо/вниз и «перевернуть» на случай, если
принтер кладёт наклейку мимо, «Пробная наклейка» — две наклейки с рамкой по краю. С выбранным
принтером наклейки уходят в него сразу, без экрана печати; без него — экран печати программы,
на сайте — окно печати браузера (бумагу размера наклейки выбирают там). На наклейке — название
с дозировкой, штрихкод с цифрами, цена на чёрной плашке; раскладку под размер считает
`client/src/lib/nakleyka.js`, штрихкоды — `client/src/lib/barcode.js`: 13 цифр с верной
контрольной — EAN-13, 8 — EAN-8, остальное (латиница, цифры, знаки) — Code 128, чтобы сканер
выдал ровно записанный у товара код; код с русскими буквами или длиннее наклейки окно не
печатает и говорит почему. Тонкости печати, без которых сканер спотыкается:
- каждая наклейка — своя страница, а размер страницы передаётся принтеру явно, в микронах:
  без него новый движок печати отдавал принтеру этикеток лист A4;
- модуль штрихкода — целое число точек принтера, левый край кода — на точке, сдвиг — целыми
  точками; на узкой наклейке белые поля кода сужаются (EAN-13 — до 9 и 7 модулей, Code 128 —
  до 6), иначе на 30×20 у принтера 300 dpi код не вставал бы;
- вся наклейка — один рисунок SVG от угла блока наклейки (`client/src/components/Nakleyka.jsx`):
  браузер подгоняет картинки к точкам экрана и сдвинул бы маленькую картинку с кодом с точек
  принтера; строки названия переносит и обрезает многоточием сама раскладка. Сдвиг и поворот —
  внутри рисунка: сдвинутое стилями содержимое вылезало бы за страницу, и движок добавлял бы
  пустую наклейку или ужимал страницу;
- блок наклейки на 0,6 мм уже и ниже страницы: движки округляют размер страницы, и наклейка
  ровно в страницу переносилась бы на следующую;
- старый движок (программа для Windows 7 и 8) правила именованной страницы `@page sticker` не
  применяет, поэтому, пока на печати наклейки, нулевые поля задаются и для страниц без имени;
  при печати он ещё и растягивает страницу на 0,1–0,45 % — проверка печатает наклейки в PDF,
  растрирует их как драйвер принтера 203 dpi и читает каждый код распознавателем.

**Меню, кассир и клавиатура (с 1.5.5).** Главное меню — одна сетка 6 колонок × 4 ряда на
любом экране, кроме телефона, без прокрутки: плитки растягиваются под экран, надписи
подстраиваются под размер плитки (единицы `cq`). Порядок плиток задал владелец магазина
(`NAV` в `client/src/components/Layout.jsx`), касса — две клетки. Шапка меню закреплена;
значков версии, отправки и касс в сети в ней и в полосе внизу больше нет — они в
«Настройках» → «Профиль» (блок «Программа», только в программе для Windows). Полоса внизу —
64 px, крупный шрифт; на главном меню в ней «Блокировка» и «Свернуть», а «Закрыть программу»
только в шапке (с 1.5.6), в разделах шапки нет — там она внизу. Сотрудник со встроенной ролью «Кассир» (сервер называет её полем
`roleSystem`; программа помнит его и для входа без интернета — колонка `accounts.roleSystem`)
плиток не видит: после входа сразу касса, «Меню» внизу — окно со списком его разделов
(`KassirMenu.jsx`). Экранная клавиатура — во всех разделах и на экране входа, только на
широком экране; лежит поверх страницы и ничего не сдвигает, открытое окно (и форма входа)
поднимается над ней, только если она его закрыла. «Печать» в окне чека закрывает окно сразу:
чек на время печати держит `PrintKeeper.jsx`. Списки разделов — без страниц: весь список
одной лентой, строки дорисовываются при прокрутке (`Pagination.jsx`). Z-отчёт — «Переводом»
всегда, с суммами по сервисам. «О компании» — всегда тёмная.

Кассы магазина (компьютеры с программой) владелец видит в «Настройках» и может назвать
по-своему; имя кассы показывается в истории смен и в расхождениях.

Нужна Windows 10 или новее, 64-разрядная.

**Проверки программы** (в папке `desktop`):

| Команда | Что проверяет |
| --- | --- |
| `npm test` | части по отдельности: расчёты, локальная база, очередь, обмен, срок без связи, копии, обновление, печать |
| `npm run test:app` | саму программу — настоящее окно и настоящий сервер: вход, касса, день без интернета, значок состояния, копия и поднятие испорченной базы, печать, собранный `.exe` |
| `npm run test:sync` | обмен с настоящим сервером без окна: продажа без интернета, возврат связи, повтор без дублей, обрыв посреди обмена, две кассы, потерянный ответ и смена пароля, округление, пересчёт остатка, давний чек, смена, закрытая владельцем, расходы без связи и из кассы, приход в долг, внесение и изъятие, чек переводом, оплата поставщику из кассы, чужой ключ кассы |
| `npm run test:parity` | расчёты кассы и сервера совпадают до дирама |
| `OLD_SRC=<desktop прежней версии> node --test test-live/upgrade.live.mjs` | обновление на компьютере магазина: базу, оставленную прежней версией программы (её исходники берутся из git), открывает нынешняя — вход без связи, неотправленный чек, первый обмен владельца |
| `npm run test:update` | настоящая установка и настоящее обновление (ставит и удаляет проверочную сборку) |
| `npm run test:release` | выложенный установщик: скачать без ключа, сверить, поставить, войти, удалить |

Четыре главных случая обмена — продажа без интернета, возврат интернета, повторная
отправка без дублей, обрыв связи посреди синхронизации — проверяются дважды: на
основной части программы (`test:sync`) и на программе целиком (`e2e/sync.spec.mjs`
в `test:app`). Для `test:app` нужны собранный интерфейс
(`npm run electron:build -- --dir`) и `APP_USER`/`APP_PASS` проверочного магазина; все
проверки, кроме `npm test`, пишут настоящие данные — запускать только на своей
проверочном магазине.

## Деплой

### Бэкенд + БД → Railway
1. New Project → Deploy from GitHub repo → выбрать этот репозиторий.
2. Root Directory: **`server`**.
3. Add **PostgreSQL** (плагин) — Railway сам подставит `DATABASE_URL`.
4. Variables: `CORS_ORIGIN` = адрес фронта на Vercel (например `https://apteka-kassa.vercel.app`).
5. Деплой. Старт (см. `server/Dockerfile`): `npx prisma db push --accept-data-loss` (синхронизирует схему БД) + `node dist/main`.
6. Скопировать публичный URL сервиса → добавить `/api`.

> **Схема БД синхронизируется `prisma db push` при каждом старте** — идемпотентно и недеструктивно:
> досоздаёт недостающие таблицы/колонки и приводит типы к `schema.prisma` (в т.ч. `Float→Decimal`)
> БЕЗ потери данных. Работает и на чистой базе, и на уже существующей.
> Демо-наполнение включается переменной `AUTO_SEED=true` (по умолчанию выключено).

### Изменения, которым нужна новая таблица или колонка у магазинов
Схемы магазинов сервер обновляет сам, в фоне, после запуска — по одному магазину (состояние
видно по `GET /api/admin/schema`). Пока очередь не дошла до магазина, новой колонки у него
ещё нет, а код уже работает. Поэтому такое изменение выкладывается в два приёма:
сначала миграция — без кода, который ею пользуется; когда она прошла у всех магазинов —
сам код. Так выкладываются кассы без интернета: миграция `20261004_kassy_bez_interneta`
отдельным коммитом, остальное — следом. Перед выкладкой серверной части стоит снять
копию каждого магазина.

### Фронтенд → Vercel
1. New Project → Import тот же GitHub repo.
2. Root Directory: **`client`**.
3. Environment Variable: `VITE_API_URL` = `https://<railway-домен>/api`.
4. Deploy.
